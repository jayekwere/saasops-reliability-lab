# Reliability architecture

A trusted catalog contains at most twenty HTTP, DNS or TLS targets. IDs are unique, dependencies must exist, and cycles/self-dependencies are rejected. Configured services seed one namespace selected by TENANT_ID. Tenant records remain isolated; identities without that catalog see empty overview state. The public API can collect the stored catalog and change an objective with version checking, but cannot insert a destination or command.

HTTP and TLS resolve and validate destination addresses before pinning the selected address to a socket. Configured mode rejects loopback, private, link-local, metadata and reserved ranges. The HTTP Host header and TLS server name preserve the intended hostname, and TLS certificate verification stays enabled. Redirects are never followed. DNS probes use the system resolver; a custom resolver is allowed only by the local lab configuration. Operator configuration, routing and system trust remain deployment dependencies.

Collection is serialized per tenant within one process. A minimum half-second interval prevents immediate duplicate polling. Each observation records actual time, outcome, reason, bounded details and measured elapsed latency. A catalog-version change during collection refuses that observation rather than silently attributing it to the new state. Source-probe timeouts are bounded. The engine does not execute configuration supplied in a request body.

Two recent consecutive failed observations open an incident if one is not already unresolved for that target. An excessive sample gap does not establish a continuous failure. The incident stores evidence IDs and runbook version. Acknowledgement, monitoring and resolution require the exact state version and a recorded note. Resolution requires the latest two target observations to succeed after detection and remain fresh. The exported investigation includes the referenced records. It does not claim user-level impact, the true start of an outage, or the cause of a matching recovery.

Reliability statistics are observed-probe success ratios, sample budget and burn calculations over retained records in the last hour. Missing data is not a success. No data gives null ratios; stale latest data gives unknown health. Window eligibility requires at least six samples, freshness, regular gaps and a span covering the relevant hour within cadence tolerance. Even an eligible sample window is not all-user or time-based availability. The UI keeps incomplete ratios labeled descriptive.

Retention prunes older unreferenced observations when the tenant reaches 5,000 records, keeping the recent 4,000 and every incident reference. A hard observation limit still fails closed. The 200-incident limit bounds retained protected evidence. The audit chain remains independent of observation pruning; there is no automatic audit archive. Operator evidence export and controlled archive are required for longer operation.

Catalog backups bind tenant, time and stored configuration through a domain-separated HMAC. Restore plans bind backup ID/digest and exact current configuration fingerprint, with independent requester/reviewer/operator identities. The local transaction covers claim, configuration update, persisted readback, completion evidence and idempotency. A changed configuration or edited backup blocks restoration. This is recovery of the service catalog only, not restoration of a remote SaaS platform or the complete service database.

The fault lab owns only private loopback HTTP endpoints and one UDP DNS responder. It answers a fixed name without recursion, accepts bounded packets and never changes host DNS configuration. Fault switches are exposed only in demo-mode app construction and require an operator role. Production configuration does not mount this lab.
